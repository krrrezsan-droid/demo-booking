## Инструменты и промпты

Использован Codex: чтение и правка файлов, Git (анализ изменений и подготовка коммитов), Docker Compose, Composer, Artisan, PHPUnit, Pint, официальная документация Laravel 13 и PHPUnit 12. Субагенты не использовались.

Ключевые задачи, поставленные ИИ. Формулировки ниже отредактированы и объединены по смыслу рабочей переписки; это не дословные цитаты.

1. **Анализ и реализация задания.** Разверни проект локально в `/srv/www/demo-booking`, изучи требования в README и проведи ревью API бронирования. Исправь создание и отмену брони по ТЗ, добавь feature-тесты и подготовь документацию.

2. **Проверка корректности.** Проверь работающий API через curl: создание, пересечения, границы рабочего времени, часовые пояса, валидацию и права на отмену. Добавь тест конкурентного бронирования с независимым процессом.

3. **Архитектура и читаемость.** Приведи код к принципам SOLID, DDD и KISS. Вынеси запросы из контроллера в сервис и скоупы, раздели тесты по сценариям и используй именованные data providers. Оформи PHPDoc с описанием параметров, результатов, свойств и связей; типы импортируй через `use`. Не добавляй лишние методы и абстракции.

## Ошибки ИИ и перепроверка решений

При подготовке тестов ИИ неверно пересчитал два интервала с часовыми смещениями. Тесты ожидали успешное создание, но API возвращал 422: один интервал оказался длиннее четырёх часов, другой попадал до открытия офиса. После пересчёта через UTC исправлены тестовые данные. Логика приложения была корректной и не менялась ради прохождения тестов.

Ещё один показательный случай — тест конкурентности. В первой версии оба запроса использовали один токен, поэтому второй процесс ждал обновления `personal_access_tokens`, а не блокировки комнаты. Проверка SQL ожидающего процесса обнаружила эту ошибку. Для клиентов созданы разные пользователи и токены; теперь тест подтверждает ожидание блокировки `rooms`, ответ 422 после коммита первой транзакции и наличие одной брони в БД.

Проверялась и способность теста обнаружить регрессию: при временном удалении `lockForUpdate` второй запрос получил 201, и тест упал. После восстановления блокировки проверка прошла.

## Проверки и самостоятельные решения

Проверки выполнялись через Codex в локальном Docker-окружении с PostgreSQL:

- **Feature-тесты:** создание и отмена, авторство, пересечения и соседние интервалы, длительность, шаг, рабочее время обоих офисов, смещения и некорректные данные. Граничные случаи оформлены именованными data providers.
- **Транзакции и логи:** проверены ожидание блокировки отдельным процессом, запись `booking_id` после коммита и отсутствие сообщения об успешном создании после отката.
- **Окружение и оформление:** выполнены `composer validate`, `composer check-platform-reqs`, Laravel Pint и `git diff --check`.

Итог последнего полного прогона: **55 тестов, 209 assertions, все прошли**.

### Ручная проверка API

Отдельно от PHPUnit выполнены живые HTTP-запросы с помощью curl. Проверены ответы 201, 204, 401, 403, 404 и 422, сохранение автора из токена, нормализация времени и повторное бронирование после отмены. Всего выполнены **46 curl-запросов**, включая очистку проверочных данных. Проверочные записи удалены.

### Самостоятельные решения

Архитектуру и читаемость я не оставлял на усмотрение ИИ. После первой реализации решил вынести запросы из контроллера в сервис и скоупы, разделить тесты по сценариям, оформить полноценный PHPDoc и убрать лишние обёртки. Отдельно настоял на проверке конкурентности и живых запросах через curl. Эти требования уточнялись по ходу работы, а не были полностью заданы первым промптом.

## Ограничения

Конкурентный тест проверяет конкретный сценарий гонки, а не поведение под массовой нагрузкой. Блокировка комнаты защищает пути записи, соблюдающие общий протокол; прямые SQL-вставки могут его обойти. Повторная отправка POST после потери ответа не обеспечивает идемпотентность: если бронь уже сохранена, повторный запрос получит 422.
